# Revision design, November 2026 (AIIPCC69233)

Owner of this design: the coordinating agent. Workers implement it; they do not change a
decision here. If a decision proves unworkable, stop and report (see each brief).

## 0. Why the October design could not show an agent benefit

- The admission gate and the compiler take the deterministic reader's own content inventory
  (`procedure-core.js` `inspect()`) as the definition of required content. `compile()` unions
  every reader block outside the model region into the rule and drops any model exclusion that
  removes one (170 dropped across the 44 pages). The accepted rule is therefore at best the reader.
- The scoring averaged about one noise check per page; the reader leaked no noise and kept
  623/627 targets. The measure was saturated by the baseline.
- The model never saw the hard pages (5 ineligible) and fixed none of the 4 reader failures.
- Generation was one shot, thinking disabled, a 12,000-character sample, output only
  `main/exclude/name`, learned from a single page, with no feedback loop.

The October study stays frozen as historical evidence. Nothing below edits its files.

## 2. References (blind)

Drafted by a Codex worker from the screenshot, DOM and URL only. The annotator must not run or
read the output of the reader, Readability, or any rule. One `reference.json` per page:

- `content`: ordered units `{id, role, text, selectorHint, required}`.
  Roles: title, byline, date, lede, heading, body, list, table, code, figure, caption, price,
  specs, description, post, comment, review, item. `required: true` for main reading content a
  low-vision reader needs. Comments/reviews are `required: false` except on discussion pages,
  where posts are required. Listing pages: entries (`item`) are required.
- `noise`: units `{id, kind, text, selectorHint}`, kinds: site-nav, related, recommended,
  share, newsletter, ad, promo, cookie, footer, author-boilerplate, widget, other. Annotate every
  boilerplate block inside or beside the main column that is visible in the screenshot, plus the
  global header and footer (at least one unit each). Aim for 5 or more where they exist.
- `neutral`: breadcrumbs, in-page table of contents, tags. Neither rewarded nor penalised.
- Unit text is copied from the DOM (normalized whitespace). Long units keep their full text.

Audit: one page per evaluation site (40 pages, 20%), chosen by seeded random draw, delivered to
the user/Randy as a Google Doc review sheet. Corrections are applied as a new reference version;
the scorer reports results on audited references and on all references.

## 3. Measures (declared before any evaluation request)

Text is NFKC-normalized, whitespace-collapsed, case kept. Text extraction (for outputs and for
reference checking alike) inserts a space at every block-level element boundary, `br`, `li`,
`td` and `th` (added 2026-11-21: adjacent blocks had merged into one token). A unit is present in an output if
token-level LCS(unit, output) / tokens(unit) >= 0.9; units under 5 tokens need an exact
substring.

- Content recall: required units present / required units (also character-weighted).
- Noise leakage: noise units present / noise units; noise character share of output text.
- Title first: title unit present and before every other required unit.
- Order: Kendall tau between reference order and output order of present required units.
- **Complete pass:** unit recall >= 0.95 and title present.
- **Clean pass:** complete pass and noise leakage <= 0.2 and order tau >= 0.9.
- **No-fallback pass:** a clean pass delivered by the policy's own rule (no reader fallback).
- Accounting per policy: model requests, prompt/completion/cached tokens, cost estimate, latency,
  failures by reason (invalid, gate-rejected, not-applicable, runtime error, budget), fallbacks.
  Invalid or unexecutable candidates count as failures; none are dropped.
- Statistics: site-clustered bootstrap (10,000 resamples over sites) for 95% intervals; paired
  site-clustered differences against the reader and against Readability; per-page win/loss counts.
- Noise character share: characters of the union of output-token spans matched by any noise
  unit's LCS alignment (partial matches included, overlaps counted once) / output characters.
- Order position of a unit (revised 2026-11-21): monotone alignment with consumption. Units are
  taken in reference order; each takes the earliest occurrence of its text that starts after the
  previous unit's position and is not used by another unit; if none exists, its earliest unused
  occurrence anywhere. An occurrence's start is its first matched token. Title-first and Kendall
  tau use these positions. (Per-unit earliest alignment gave a title and an identical lede the
  same position, a tie that failed correct outputs.)
- References: two units with identical text are valid only if that text occurs at least that
  many times in the page; `check-reference.cjs` reports violations.
- Development may calibrate the 0.9 / 0.95 / 0.2 thresholds; they freeze before evaluation.

## 5. Rule format v3

```json
{
  "schemaVersion": 3,
  "name": "Product page",
  "applicability": { "anchors": [ { "selector": "div.product-main", "min": 1, "max": 1 } ] },
  "regions": [
    { "role": "title", "selector": "h1.product-title", "multiple": false, "required": true },
    { "role": "price", "selector": ".price-box", "multiple": false, "required": false },
    { "role": "description", "selector": "#description", "multiple": false, "required": true },
    { "role": "specs", "selector": "table.specs", "multiple": false, "required": false },
    { "role": "review", "selector": "li.review", "multiple": true, "required": false }
  ],
  "exclude": [ ".share-bar", ".related-products" ],
  "reveal": [ "details", ".tab-panel" ],
  "provenance": { "model": "...", "inductionPages": 2, "createdAt": "..." }
}
```

- Roles are those of section 2 plus `body` and `other`. Regions render in the declared order,
  each wrapped in a `section` with `data-role`; a title that is not a heading renders as `h1`.
- Selectors: valid CSS, no positional pseudo-classes, at most 300 characters, matched outside
  the existing NOISE filter. A non-`multiple` region must match exactly once on every page it is
  applied to; `required` regions must match. `reveal` removes `hidden`, `aria-hidden`, inline
  `display:none` and sets `details[open]` inside regions.
- Rendering reuses `procedure-core` `clean()` sanitization semantics (no scripts, handlers,
  form values, unsafe URLs; relative URLs resolved).
- Implementation: new UMD module `extension/procedure-v3.js`. `procedure-core.js` stays
  unchanged so P0, P2 and P2-nr reproduce the October behaviour.

## 6. Agent loop

One request per turn, uniform JSON-action protocol for every model (no provider tool-calling,
so models are comparable). Each turn the model returns exactly one action:

- `{"action":"outline","page":k,"node":id,"depth":d}`: de-identified skeleton lines
  `[id] tag#id.class[role] children=n text=c links=0.42 repeat=2/2 "cue..."`.
  The first message carries the top-level outline of each page (at most 8,000 characters per
  page; deeper subtrees collapsed and expandable).
- `{"action":"query","selector":"..."}`: per page, match count and for the first 5 matches:
  node id, text length, link density, repeat flag, cue.
- `{"action":"preview","rule":{...}}`: per page, gate verdict and reasons, outline of the
  rendered output (first 40 blocks with cues), output text length, coverage of the page's unique
  substantive blocks, template blocks retained, cues of unique blocks missing.
- `{"action":"submit","rule":{...}}`.

Budget: 6 turns; the last turn must submit; a missing or invalid final rule is a counted failure.
`repeat` (cross-page evidence) marks a block whose normalized text (>= 20 characters) occurs on
both induction pages: a template block. P3 has no repeat evidence; it sees link density and
position only. The system prompt states the task, the schema, and guidance: title first;
keep the body, in-content navigation, figures, code and tables; for products keep description
and specs; remove blocks that repeat across pages, global navigation, share/related/promo
blocks. The prompt is frozen before the first evaluation request and hashed into the ledger.

### 6a. Capability programme: surpass the rule-based readers (2026-11-21)

Target: P4 beats P0 (reader) and P1 (Readability) on clean pass and noise leakage on held-out
pages. Levers, applied and measured on development sites only, kept when the development
scoreboard improves:

1. **Baseline-seeded refinement.** The first message also shows, per induction page, the
   containers P0 and P1 choose and the outline of their outputs with repeat flags. The agent's
   job is to correct them: drop evidence-backed noise they keep, add content they miss, label
   roles. This makes "at least as good as the better baseline" the starting point, not the goal.
2. **No-regression gate (reference-free).** G6: the rule keeps every unique, non-sidebar,
   substantive block that the better-covering baseline keeps on each induction page, unless the
   block is template (repeat), sidebar, link density >= 0.3, or under 40 characters. Additions
   are always allowed. Noise can then only be removed on evidence, and content cannot regress.
3. **Suspicion lists in preview.** Preview lists kept blocks that look like boilerplate (repeat,
   high link density, class/id tokens such as share, social, related, recommend, promo, ad,
   newsletter, subscribe, cookie, comment-form, breadcrumb, footer) and dropped blocks that look
   like content, so the agent can fix both before submitting.
4. **Families.** A site may hold several rules with distinct anchors; the use-time check picks
   the rule whose anchors match, else falls back.
5. **Model settings.** DeepSeek thinking on vs off and the local model are compared on the
   development scoreboard; Codex runs as an upper-bound reference on a subset.
6. **Harder development sites.** Development adds 4 sites of the hard types (product, forum,
   client-rendered, unmarked layout) so tuning sees what the evaluation stresses.

Development scoreboard (scored with section 3 against development references): clean pass,
recall, noise leakage, no-fallback pass for P0, P1, P3, P4 per site. The prompt, gate
parameters and views freeze, with hashes in the ledger, before the first evaluation request.

## 7. Deterministic gate (reference-free, reader-free)

"Substantive block": p, li, td, th, dd, pre, blockquote, figcaption, h2-h6 with >= 40
characters and link density < 0.5, outside the NOISE filter. "Unique" at induction: not a
template block.

Induction (every induction page; P3 uses its single page):
- G1 schema and selectors valid; region match counts as declared on every page.
- G2 the page's H1 text (if one exists outside NOISE) is in the output.
- G3 output keeps >= 90% (character-weighted) of unique substantive blocks (P3: >= 80% of all
  substantive blocks).
- G4 each exclusion tested alone: rejected if it removes a unique substantive block.
- G5 output text >= 200 characters.

Use time (one page, in the browser): applicability anchors match; G1, G2, G5; the output's
substantive-text ratio is within [0.5, 2] x the induction median ratio. Failure: automatic
reader fallback, with the reason logged. The reader's inventory is never part of the gate.

### 7a. Gate revisions after development run 1 (2026-11-21, coordinator decision)

- Rules are bound to their hostname, as in deployment. Applicability anchors must include at
  least one selector with a class or id token; bare `main`, `article`, `body` or
  `[role=main]` anchors alone are not accepted. The cross-site pairs stay as a stress measure.
- "Sidebar" = inside `aside`, `[role=complementary]` or `nav`. Sidebar blocks do not count
  toward the G3 floor, and G4 allows excluding a unique block that is in a sidebar, has link
  density >= 0.3, or is under 40 characters. (Run 1: per-page related stories on BBC counted as
  unique and blocked their removal.)
- G5 becomes: output >= min(200, 0.5 x the page's substantive characters). (Short discussion
  threads failed the fixed 200.)
- The use-time ratio check is replaced by a use-time coverage floor: the output keeps >= 60%
  (character-weighted) of the page's substantive non-sidebar blocks; plus anchors, G1, G2, G5.
- The system prompt may recommend one broad reading container only together with excluding the
  template and boilerplate blocks inside it; the agent's added value is the exclusions and roles.
- Development pages whose final URL leaves the site's host are replaced (W3C p2 redirected).

## 8. Privacy and user protection (extension)

- Only the de-identified outline, query results and previews reach the model provider. Cues are
  the first N characters of a block (N = 60 default) after redaction: emails, phone numbers,
  URLs (host kept), digit runs of 3 or more -> `#`, @handles, form values removed. Redaction does
  not remove names or free-text personal details; this is measured, not claimed.
- The full sanitized DOM stays on the user's machine (local backend on 127.0.0.1 acts as the
  service in this prototype). In the shared design users contribute examples with consent and a
  central service generates, validates and publishes; the prototype does not demonstrate that.
- No automatic upload: a missing, failed or rejected rule shows the basic reader view. The side
  panel shows what would be sent (provider, character count, a redacted sample) and a button to
  request a new rule. A second page of the same family is kept locally only after consent.
- Manual fallback: a "Basic view" switch is always available; "Report problem" retires the rule.
- Redaction audit: every outbound payload is saved under `workspace/revision/payloads/`; a
  script counts residual patterns, and a 40-payload sample is reviewed for missed personal data.

## 9. Ledger and spending

`workspace/revision/ledger.jsonl` records every model request: policy, model, page/site, turn,
tokens, cost estimate, payload hash, prompt hash, outcome. A guard refuses a paid request once
the approved cap is reached: DeepSeek $5.00 total and 2,000 requests (raised from 1,000 by the user
on 2026-11-20). Development may use at most 450 paid requests (raised from 250 by the coordinator on
2026-11-21 for the capability programme; within the user's 2,000 total). Codex and pc11 requests are
logged but not counted against the DeepSeek cap.
